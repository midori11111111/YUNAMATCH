# セキュリティ・個人情報事故対応手順

最終更新: 2026-08-26

対象: YUNAMATCH、バロマッチ、スタメイト、荘園メイト

この文書は初動漏れを防ぐ運営手順であり、法的助言ではない。事故時は個人情報保護委員会、所管総合通信局、委託先および必要に応じて専門家へ確認する。

## 1. 事故を検知した直後（0〜30分）

1. 発見日時、発見者、対象サービス、症状を記録する。
2. 漏えい拡大を防ぐため、該当API・認証・管理操作だけを停止する。証拠となるログやデータは削除しない。
3. 管理者パスワード、OAuth秘密鍵、APIキーの流出が疑われる場合は、影響範囲を確認して失効・再発行する。
4. データベース、ホスティング、OAuth事業者のアクセスログとデプロイ履歴を保全する。
5. 通常DMは一括閲覧せず、事故調査に必要な最小範囲だけを扱う。

## 2. 影響範囲の確認（30分〜3時間）

- 何が起きたか: 不正ログイン、誤公開、脆弱性、権限誤設定、端末紛失など
- 対象者数と対象サービス
- 対象情報: ログイン識別子、メール、プロフィール、年齢、性別、チャット、IP、通知情報など
- 外部流出の有無、閲覧・取得・改ざん・削除の可能性
- 要配慮情報、未成年者情報、財産的被害、不正目的の可能性
- 発生期間、現在も継続しているか

判断と根拠は `日時 / 担当 / 確認内容 / 証拠 / 次の対応` の形式で残す。

## 3. 連絡と報告

1. 個人情報保護委員会の「漏えい等の対応」を確認し、報告対象なら速報・確報を行う。
2. 本人通知が必要な場合、事実、対象情報、原因、二次被害防止策、問い合わせ先を分かりやすく通知する。
3. 電気通信役務や通信の秘密に関係する事故は、所管総合通信局への報告要否を確認する。
4. Cloudflare、認証事業者など委託先の事故窓口と契約条件に従って連携する。
5. 公表する場合は推測を書かず、確認済み事実と未確定事項を分ける。

## 4. 復旧条件

- 流出経路または誤設定を封じた
- 侵害された認証情報を失効した
- 修正コードをレビューし、テスト環境で再現防止を確認した
- 管理者ログ、通報、ブロック、退会が正常に動く
- 監視項目と再発防止策を追加した
- 必要な報告・本人通知の担当と期限が決まった

## 6. 定期訓練

- 月1回: 管理者ログ、通報対応、停止・復旧、退会処理を確認
- 四半期1回: 秘密鍵流出を想定した失効・再発行訓練
- 大型公開前: バックアップ復旧、権限、負荷、脆弱性、未成年者導線を確認
